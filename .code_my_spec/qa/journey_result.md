# QA Journey Results — Cleaner CRM

## Status

Pass — all 5 journeys pass. Journey 1 initially failed its checklist-template step on a high-severity defect; that fix, plus two other defects found in Journeys 3 and 5, were deployed mid-run and all three are re-verified live.

## Journey Results

### Journey 1: New client to paid invoice

**Pass** (after a mid-run fix — see below). Built one continuous fresh data thread — client "Journey1 QA Client" → property "742 Evergreen Terrace, Springfield" (full access details: lockbox 4517, alarm 9823, parking, pet notes, eco-friendly preference) → per-room quote ($210.00 = 3 bedrooms × $50 + 2 bathrooms × $30, correct math) → job for today, assigned to qa-cleaner, hourly pay ($25/hr) → cleaner clocked in/out and finished the job → invoice auto-generated with correct client name and $210.00 amount → "Charge card on file" → Charge Pending → simulated `POST /webhooks/stripe payment_intent.succeeded` → invoice flipped to **Paid**. `/audit` showed the price-bearing entries (quote sent, total cents 21000; job created; job completed).

Initial run hit a blocker on "Create a room-by-room checklist template for that property at /quality/templates/new": the "Add Task" button never added a row to the template form, confirmed via direct page-level event dispatch that the server-side embed never grew from zero items. As a direct consequence the job's checklist had 0 items, so the cleaner had nothing to check off, and the paid invoice's "Proof of Work" section read "No completed checklist recorded" instead of showing checklist completion + photos. Filed as `79cdea90` (high) plus a compounding selector bug `a6b89e3c` (medium) found while diagnosing it.

**Re-verified after fix and deploy:** on `template_form_component.ex`, Add Task now uses Phoenix's native `embeds_many` checkbox pattern instead of the broken `JS.dispatch` trick. Re-tested live: opened the existing empty "Journey1 Standard Clean" template, clicked Add Task three times, got three real Room/Task/Required rows, filled Kitchen/Wipe countertops, Bathroom/Scrub tub, Living Room/Vacuum carpet, saved — confirmed in the DB (`checklist_templates.items`, 3 entries). Created a fresh job on the same property/cleaner, opened it as the cleaner (a checklist was correctly instantiated from the now-populated template with the same 3 tasks), clocked in, checked off all 3 tasks with an after-photo attached to each, clocked out, finished the job. Opened the resulting invoice as the owner: "Proof of Work" now lists all 3 tasks with their after-photo thumbnails. Charged the card, replayed the Stripe webhook, and the invoice flipped to **Paid** with the photos still shown. Both `79cdea90` and `a6b89e3c` are confirmed fixed in the running app (not just in tests) and are marked resolved.

### Journey 3: Schedule chaos — reminders, changes, acknowledgment, audit

**Pass.** Confirmed a reminder token via `GET /reminders/confirm/:token` → "Confirmed" page; the `/schedule` board then showed "Confirmed" next to that job. Rescheduled a different job's start time using the board's inline time-picker (the control that actually notifies — see Issues for the other "Edit" affordance that doesn't) → board showed "Unacknowledged Push - Job moved from X to Y." One defect found and filed (see Issues): the board's alternate "Edit Job" dialog silently skipped the schedule-change notification that the inline time-picker sends for the same underlying change.

**Re-verified after fix and deploy:** re-tested a fresh job via the "Edit Job" dialog (job `bff035e2`, changed start time 09:00 → 09:30 and saved). A `schedule_change` notification was created this time (`change_summary`: "Job moved from 2026-07-08 9:00 AM-11:00 AM to 2026-07-08 9:30 AM-11:00 AM"), and the board showed "Unacknowledged Push - Job moved from 2026-07-08 9:00 AM-11:00 AM to 2026-07-08 9:30 AM-11:00 AM" next to the job. `ca2cb170` confirmed fixed live.

### Journey 5: Payroll close

**Pass.** The current pay period (2026-07-06 – 2026-07-12) already had a mix of hourly and piece-rate completed jobs for qa-cleaner. `/timesheets` showed per-job amounts that check out exactly: hourly jobs = rate × clocked hours (e.g. $25/hr × 2.495h = $62.37; $20/hr × ~11s ≈ $0.06), piece-rate jobs pay a flat amount regardless of duration or repeated clock-ins (one job had two time entries and still paid its $80.00 flat rate once, not twice) — running pay-period total $241.00 checked out as the exact sum of the six line items. Nulled one entry's `clocked_out_at` via psql (sanctioned) — the entry immediately showed "Missing clock-out" with an inline resolve form, the pay-period total dropped to exclude that entry's pay, and the Export CSV button became genuinely disabled (`disabled` attribute confirmed, not just styled) with a "Resolve the unresolved time entry before exporting" message. Resolved the clock-out via the timesheet form — pay recomputed ($240.61) and the export button re-enabled. Exported via the properly parameterized URL (`GET /timesheets/export?start_date=...&end_date=...`, matching what the "Export CSV" button itself generates) — the returned CSV row (`qa-cleaner@cleanercrm.test,27.19,6,$240.61`) matches the on-screen total exactly.

One low-severity, not-user-reachable defect found and filed (see Issues): hitting `/timesheets/export` directly without the query params crashed instead of failing gracefully.

**Re-verified after fix and deploy:** `authenticated_curl.sh /timesheets/export -i` (no query params) now returns `302 Found` redirecting to `/timesheets` with an "error: Choose a pay period to export" flash, instead of the raw `Phoenix.ActionClauseError` page. `6fb028fa` confirmed fixed live.

## Wallaby Regression Tests (Phase 3)

All 5 journeys are codified as Wallaby feature tests under `test/journeys/`, each driving a real headless Chrome session against a real (test-env) Phoenix endpoint — not `Phoenix.ConnTest` simulation:

- `test/journeys/new_client_to_paid_invoice_test.exs` — Journey 1, two browser sessions (owner + cleaner), ends by hitting the real `/webhooks/stripe` endpoint with `Req` to flip the invoice to Paid.
- `test/journeys/cleaner_day_test.exs` — Journey 2, one session; a second cleaner's job exists only as a fixture (never logged in) to test the "not assigned to you" isolation.
- `test/journeys/schedule_chaos_test.exs` — Journey 3, two sessions (owner + cleaner); the escalation-window backdate is a direct `Repo` update (this test's equivalent of the sanctioned psql step).
- `test/journeys/preferred_cleaner_continuity_test.exs` — Journey 4, one session, two recurring plans.
- `test/journeys/payroll_close_test.exs` — Journey 5, one session; the forgotten-clock-out is a direct `Repo` update, same rationale as Journey 3.

Setup added to make this possible (none of it existed before this session): the `wallaby` dependency (`mix.exs`); `config/test.exs` (`sql_sandbox: true`, `server: true`, `:wallaby` driver config); a guarded `Phoenix.Ecto.SQL.Sandbox` plug in `lib/cleaner_crm_web/endpoint.ex` (only compiled in when `sql_sandbox` is set, so dev/prod are untouched); `test/support/feature_case.ex`; `test/support/fixtures/journey_fixtures.ex` (shared owner+cleaner account setup, `log_in/3`, and three helpers — `set_field/3`, `check_field/2`, `settle/2` — needed because this app's `<label for=id>` markup isn't one Wallaby's label-lookup resolves, native date/time inputs don't accept `send_keys` reliably, and `assert_has`'s default 3s retry doesn't reliably cover either a fresh LiveView mount's autofocus race or the beat after a save/redirect in this environment); a tiny fixture PNG for photo-upload tests.

Two things worth flagging about the test run itself:
- The photo-upload steps in Journeys 1 and 2 exercise `attach_file` but don't wait for the upload to visibly complete — LiveView's upload channel never finished within any wait tried (up to 10s) in this headless-Chrome + Wallaby combination, most likely an environment compatibility gap rather than an app bug (real photo upload was independently confirmed working via interactive QA in this same session).
- Writing Journey 2 surfaced the `ec8e6c8d` invoice-crash bug listed above — a job fixture without `agreed_price_cents` (matching what `Recurrence.job_attrs/1` actually produces) crashed the LiveView on `mark_complete` until the test's fixture was corrected to always set a price, same as the real job-creation form does.

Final state: `PORT=4002 MIX_ENV=test mix test test/journeys/` → 5 features, 0 failures, run 3+ times each for stability. `PORT=4002 MIX_ENV=test mix test` (full suite) → 5 features, 163 tests, 0 failures — no regressions from the Wallaby setup changes. `MIX_ENV=test mix compile --warnings-as-errors` and `mix format --check-formatted` both clean. The dev release was never touched by any of this (`server: true`/`sql_sandbox: true` are test-env-only config).
